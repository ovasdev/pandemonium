# Pandemonium Bot — Взгляд техлида

## Архитектурная оценка

Pandemonium — это bridge-сервис: Telegram на входе, Claude Code CLI на выходе. Ключевая ценность — в том, что бот *не пытается быть умным*. Он не парсит промпты, не интерпретирует результаты, не кеширует ответы. Просто надёжный транспорт с протоколированием.

С точки зрения архитектуры — это ровно то, что нужно для MVP, и сделано без лишнего.

## Что сделано правильно

### Чёткое разделение ответственности

Слои изолированы корректно:
- `claude/` — subprocess management. Ничего не знает о Telegram.
- `session/` — координация. Знает и о Claude, и о Telegram, но не реализует ни то, ни другое.
- `bot/` — presentation layer. Только Telegram API.
- `storage/` — persistence. Файловая система, без зависимостей от остальных слоёв.

Это не просто «код разложен по папкам». Зависимости идут в одну сторону: `bot → session → claude`, `session → storage`. Обратных зависимостей нет. Единственное исключение — ленивый импорт `format_status_message` в `_finalize`, но это осознанный выбор, а не архитектурный дефект.

### Единая точка координации

`SessionManager` — God Object? Нет. Это *координатор*. Он единственный, кто знает о всех подсистемах, потому что это его работа. Альтернатива — размазать координацию по хендлерам, и получить спагетти. Текущий дизайн правильный.

### Конфигурация через Pydantic

`AppConfig` с field validators и properties — минимальная, но достаточная валидация. Проекты, пользователи, лимиты — всё типизировано. `_ensure_bot_project` гарантирует, что бот сам всегда в списке. Продуманно.

### Протоколирование

Файловое хранилище сессий (`request.md`, `stream_log.md`, `report.md`, `meta.json`) — это не фича, это инфраструктура для отладки. Когда что-то пойдёт не так (а оно пойдёт), эти файлы сэкономят часы. Отдельный респект за `meta.json` с аккумулированными токенами.

## Архитектурные решения, которые я бы обсудил

### Один активный запрос на весь бот

Сейчас `SessionManager._active` — один слот. Это означает: один пользователь блокирует весь бот. Для single-user setup — нормально. Но если завтра будет два пользователя, или один пользователь захочет параллельные запросы к разным проектам — нужен рефакторинг.

Решение не сложное: `dict[int, ActiveSession]` с ключом по `chat_id` или `user_id`. Но менять нужно будет и `SessionManager`, и `handlers`, и `callbacks`. Это тот случай, когда лучше заложить расширение сейчас, пока кодовая база компактная.

### Персоны только для дефолтного проекта

`_build_persona_prompt` работает только когда активный проект — pandemonium-bot. Для внешних проектов персоны игнорируются. Это осознанное ограничение или технический долг? Если у проекта `downloader` есть свои персоны в `.agent/personas/`, они не будут использованы. Стоит обсудить, нужна ли поддержка персон per-project.

### SQLite как единственный source of truth

Две таблицы: `requests` и `interactions`. Для текущего масштаба — идеально. Но SQLite не поддерживает concurrent writes (WAL mode помогает, но не полностью). Если бот станет multi-user или multi-instance, придётся мигрировать. Не предлагаю менять сейчас, но хочу зафиксировать ограничение.

### Отсутствие тестов

В коде нет ни одного теста. Для MVP это допустимо, но по мере роста — это бомба замедленного действия. Особенно для `StreamBuffer`, `md_to_telegram_html`, и `parse_event` — это чистые функции, которые идеально тестируются.

## Кросс-модульные наблюдения

### Совместимость со стеком FileStorage2

Pandemonium использует тот же паттерн, что и наши сервисы:
- Pydantic для конфигурации и валидации
- Async-first архитектура
- Файловое хранилище для протоколов (у нас — MinIO, здесь — файловая система)
- YAML-конфигурация

Если захотим интегрировать — например, загружать отчёты в FileStorage2 или показывать историю сессий в Marginalias — API-контракты будут совместимы.

### Паттерн subprocess management

`ClaudeProcess` — чистая обёртка над `asyncio.create_subprocess_exec`. Graceful shutdown через SIGTERM → timeout → SIGKILL. Стриминг stdout через `async for`. Сбор stderr для диагностики. Это паттерн, который можно переиспользовать в других проектах, где нужен subprocess с stream-парсингом.

### Event-driven dispatch

`match/case` по типам событий (`SystemEvent`, `AssistantEvent`, `ToolUseEvent`, `PermissionRequestEvent`, `InputRequestEvent`, `ResultEvent`) — это аккуратный pattern matching. Не нужен EventBus, не нужен Observer. Типы данных сами описывают контракт. Правильный уровень абстракции.

## Приоритеты развития (моё видение)

1. **Тесты** — хотя бы для buffer, markup, events, config. Это фундамент.
2. **Multi-session** — dict вместо single slot. Разблокирует параллельную работу.
3. **Персоны per-project** — унификация: если `.agent/personas/` есть в любом проекте, использовать их.
4. **Health endpoint** — простой HTTP-сервер для мониторинга (alive, active sessions, token usage). Наш DevOps оценит.
5. **Интеграция с FileStorage2** — отчёты как файлы в Marginalias, теги по проектам и датам. Но это уже Phase 2.

## Резюме

Pandemonium — компактный, чистый bridge-сервис с правильными архитектурными решениями. Нет over-engineering, нет premature abstractions. Код читается, слои разделены, flow прозрачный. Единственные два вопроса, которые я бы поднял на review: тесты (их нет) и single-session limitation (которое ограничит масштабирование).

Как техлид, я одобряю этот код для production в текущем scope. При расширении — нужен roadmap по пунктам выше.
